# Music Recs

Enter artists you like → get song recommendations (preview + reason) → explore deeper from any record → a blind test measures how good the recommendations are. The spec is in `SPEC.md`; decisions already made are in `docs/ai-log.md` (when they disagree, the decision wins).

## Stack

Nuxt 4 (Vue 3) + strict TypeScript, Pinia, Tailwind, VueUse, Postgres 17 (Docker locally) + Drizzle ORM, zod, Vitest + `@nuxt/test-utils`, Playwright, pnpm, Node 24 LTS. Deployed on Vercel + Neon.

## Commands

Run `nvm use` first (Node 24; Nuxt doesn't support Homebrew's Node 25).

| Command | Purpose |
|---|---|
| `pnpm dev` | Dev server at http://localhost:3000 |
| `pnpm test` / `pnpm test:watch` | All Vitest projects: `unit` (pure functions in `server/` and `shared/`), `db` (`*.db.test.ts` against `music_test`; run `pnpm db:up` first), `nuxt` (components in `app/`, happy-dom) |
| `pnpm test:unit` / `pnpm test:db` | One project only |
| `pnpm typecheck` | `nuxt typecheck` (vue-tsc) |
| `pnpm lint` | ESLint (`@nuxt/eslint`) |
| `pnpm db:up` / `pnpm db:down` | Local Postgres 17 (Docker, port 5434; dev DB `music`, test DB `music_test`) |
| `pnpm db:generate` / `pnpm db:migrate` | Generate / apply migrations with drizzle-kit (schema in `server/db/schema.ts`) |
| `pnpm db:studio` | Drizzle Studio for browsing tables |
| `pnpm db:sandbox` | psql into `music_test` |
| `pnpm record:lastfm` | Re-record `server/lastfm/fixtures/` from the real Last.fm API (needs `LASTFM_API_KEY` in `.env`; tests don't) |
| `pnpm record:itunes` | Re-record `server/itunes/fixtures/` from the real iTunes Search API (no key needed) |

CI (`.github/workflows/ci.yml`) runs typecheck → lint → test.

## Conventions

- **TDD**: write a failing test → write the least code to pass → refactor. Every feature has a test before its implementation.
- The recommendation algorithm, sorting and rating statistics are pure functions in `server/utils/`, with tests next to the file (`*.test.ts`).
- External API (Last.fm, iTunes) and LLM responses are always validated with zod. Tests use recorded fixtures, never the real APIs.
- Environment variables are read through zod schemas, never directly from `process.env`.
- **UI theme**: retro-modern futuristic cyberpunk, with colors from my reference illustration (flat pink background, teal sun, thick navy ink lines, slate, plum, coral). Use only the tokens in `@theme` in `app/assets/css/main.css` (`bg-pink`, `text-ink`, `bg-teal`…) and `font-wide` (wide Archivo headings), never raw colors; add a token if one is missing. Flat fills and thick ink lines (`border-3 border-ink`); **no gradients, glows, shadows or monospace fonts**. Panels have square corners; the only circle is the sun. Effects wait for the day 7 polish.
- **No `!important`** (including Tailwind's `!` modifier). When rules conflict, make them mutually exclusive with variants (`short` / `tall` / `wide` in `main.css`, or `max-*` ranges) instead of relying on order.
- **UI motion**: interaction feedback (cards entering, test reveals, button presses) uses Motion for Vue (`motion-v`), not hand-written CSS transitions. Use `layout` animations for reordering and `AnimatePresence` for enter/exit; take timing and spring values from `app/utils/motion.ts`. Keep `MotionConfig reduced-motion="user"` in `app.vue`: it respects the system's reduced-motion setting.
- **Everything is in English**: UI copy (page text, `aria-label`, `alt`, error messages), code comments and docs.
- **Comments only where needed**: explain why (background, pitfalls, trade-offs), not what the code already says. Keep them short. Test names describe behavior, so tests rarely need comments.
- No personal data; nothing that identifies a user beyond the anonymous ID.
- Don't touch migrations unless the schema changes; migrations are always generated by drizzle-kit.
- Commit only when I say so.

## How we work

My background: frontend engineer (4 years of React and TypeScript, some Vue). On my previous project (job-alert-triage) I learned Postgres, Drizzle, API routes, transactions, idempotent writes, advisory locks and evals.

This project keeps that project's learning loop, plus TDD:

1. **Concept first**: explain new concepts with frontend analogies and add them to `docs/concepts.md`.
2. **Demo** (Claude): write the tests first and explain in plain words what each one checks; then write the implementation and walk through it.
3. **See the result**: not just green tests, but the result itself: the page, the API's JSON, the tables in Drizzle Studio.
4. **My turn**: Claude gives a failing test and hints, and I write the implementation. When I'm stuck, give hints first; give code only when I ask.
5. **Review** (Claude): ask "what if…" questions and have me add a test case.

Exercise rules:

- Exercises go in `docs/exercises/NN-<topic>.md`. Unfinished functions throw `new Error("TODO: exercise N")`, and their tests start red.
- Copyable code blocks must run as-is, with no `?` placeholders.
- One new concept per exercise.
- The schedule is one week, so exercises are small: each fits in 30 minutes.

After each step, explain: the concept used, why it's designed this way, alternatives and trade-offs, and how I can verify it myself.
